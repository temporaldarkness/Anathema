## 1. Зачем это нужно

Движок «Аспектов» — **детерминированная система**: `createGame(seed)` + команды → `GameState`. Боты играют по правилам и принимают решения локально. Это значит, что любую партию можно **воспроизвести** и **проанализировать**.

`@aspects/simtools` — слой поверх движка и ботов, который:
- прогоняет **сотни партий** и собирает статистику;
- **сравнивает** ботов, колоды, карты;
- **детектирует** проблемы баланса, pace, AI;
- **ищет** оптимальные колоды генетическим алгоритмом.

**Чего эти инструменты НЕ делают:**
- Не играют «по-честному» в реальном времени (только симуляция).
- Не заменяют playtest с живыми людьми. Это инструменты **диагностики**, не **балансировки**.

## 2. Концептуальная модель

Три ключевых понятия, без которых не работают инструменты:

### 2.1. Series (серия)

**Серия** — единица релиза контента. Идентификатор — `meta.id` в `data/packs/<dir>/meta.json`. Примеры: `classic`, `stormwind`, `throne`.

Карта принадлежит **одной или нескольким сериям** (при рестайле).

Папка на диске ≠ `meta.id` (например, `old_stormwind/` содержит `id: "stormwind"`).

### 2.2. Scope (набор серий)

**Scope** — набор серий, в рамках которого допустимо колодостроение. Определён в `packages/cards/src/scopes.ts`.

| Scope | Серии | Назначение |
|---|---|---|
| `main` | `classic`, `cradle`, `inner`, `throne` | Основная игра, фокус баланса |
| `azeroth` | `stormwind`, `voidflame`, `apocryph` | Legacy-пак 1 |
| `svo` | `steel`, `echo`, `razlom`, `sky` | Legacy-пак 2 |

Колода должна целиком лежать в одном scope. Кросс-scope колоды — **ошибка**.

Можно передавать **явный список серий** через запятую: `classic,throne` — для экспериментальных scope'ов.

### 2.3. Preset (пресет)

**Пресет** — готовая колода (30 карт), лежит в `data/presets.json`. Идентификатор — `preset.id` (например, `strazha`).

Пресет **может** быть в нескольких scope'ах, если его карты подходят.

### 2.4. Bot (бот)

Боты живут в `@aspects/bot`. Их 36 штук:
- 6 профилей: `balanced`, `aggro`, `defensive`, `control`, `opportunist`, `berserker`
- 6 уровней: `rookie`, `novice`, `regular`, `veteran`, `master`, `grandmaster`

Идентификатор: `heuristic-v5-<profile>-<level>`.

Профиль — это веса оценки (агрессивность, защита, love к замене). Уровень — вероятность ошибки (`mistakeRate`).

Уровень **влияет на силу**, но не радикально. `grandmaster` играет чисто, `rookie` — с ошибками 15-20%.

## 3. Архитектура и установка

### 3.1. Где живёт

```
packages/simtools/
├── src/                     # библиотечный код (экспортируется)
│   ├── index.ts
│   ├── types.ts             # интерфейсы
│   ├── bots.ts              # реэкспорт из @aspects/bot
│   └── runner.ts            # runOneGame, runSeries, pickResponder
└── scripts/                 # CLI-инструменты
    ├── list.ts
    ├── simulate.ts
    ├── matrix.ts
    ├── ...
```

### 3.2. Зависимости

`@aspects/simtools` → `@aspects/engine`, `@aspects/cards`, `@aspects/bot`.

Обратных зависимостей нет. Backend и frontend могут использовать simtools, но не наоборот.

### 3.3. Установка и сборка

```bash
pnpm install                         # если менялись package.json
pnpm --filter @aspects/simtools build
```

### 3.4. Запуск

```bash
pnpm run --filter @aspects/simtools <команда> [args]
```

Или напрямую:
```bash
pnpm --filter @aspects/simtools exec tsx scripts/<file>.ts [args]
```

**Тонкость:** `pnpm run --filter X list` работает, но `pnpm --filter X list` — нет (встроенная `list` перехватывает). Всегда `pnpm run` для наших скриптов.

## 4. Runner API — фундамент

Все CLI-скрипты используют общий слой `runner.ts`. Если пишешь новый инструмент — работаешь через него, а не дёргаешь `createGame` напрямую.

### 4.1. `resolveDeck(series, deckId)`

Находит пресет по id в рамках scope. Бросает ошибку, если пресета нет.

```ts
import { resolveDeck } from '@aspects/simtools';

const deck = resolveDeck(['classic', 'throne'], 'strazha');
// → DeckPreset { id, name, cards: string[] }
```

### 4.2. `pickResponder(state)`

Определяет, кто должен отвечать командой в текущем состоянии:
- при `pendingChoice` — игрок, которому адресован выбор;
- в `MULLIGAN` — по очереди `p1`, потом `p2`;
- иначе — активный игрок;
- `null` — если партия завершена или нечего делать.

```ts
const responder = pickResponder(state);
if (responder === null) break;
const cmd = bots[responder].chooseCommand(state, responder);
```

### 4.3. `runOneGame(series, p1DeckId, p2DeckId, seed, opts)`

Одна партия между **пресетами**.

```ts
interface RunOptions {
  bots: { p1: Bot; p2: Bot };
  useMulligan?: boolean;    // default false
  maxSteps?: number;        // default 20_000
  onAfterCommand?: (state: GameState, cmd: Command, events: GameEvent[]) => void;
}

const r = runOneGame(['classic'], 'strazha', 'divan', 'seed-1', {
  bots: { p1: makeBot('heuristic-v5-balanced-master'),
          p2: makeBot('heuristic-v5-aggro-master') },
  useMulligan: true,
});
// → { winner, winnerReason, turns, steps, hitLimit, finalState }
```

**Что делает:**
1. `cardsForScope(series)` → `cardDefinitions`
2. `createGame(...)` → начальное состояние
3. Цикл: `pickResponder` → `bot.chooseCommand` → `applyCommand`
4. Возвращает результат + финальное состояние

**Что важно:**
- `onAfterCommand` вызывается **после** каждой применённой команды. Используется для сбора метрик (pace-report, combat-efficiency).
- Если `pendingChoice` и бот вернул `null` — цикл прерывается, `hitLimit = true`. Это обычно баг бота, не движка.

### 4.4. `runOneGameRaw(series, p1Cards, p2Cards, seed, opts)`

То же самое, но принимает **массивы card ids**, не пресеты. Нужен для `deck-optimizer` (у него нет пресетов) и `keyword-stats` (там оппоненты — геномы).

### 4.5. `runSeries(opts)`

Серия партий между двумя пресетами. Возвращает агрегат:

```ts
interface RunSeriesOptions {
  series: string[];
  p1DeckId: string;
  p2DeckId: string;
  games: number;
  useMulligan?: boolean;
  botFactories?: { p1: () => Bot; p2: () => Bot };
  maxSteps?: number;
}

const r = runSeries({
  series: ['classic'],
  p1DeckId: 'strazha',
  p2DeckId: 'divan',
  games: 100,
  botFactories: { p1: () => makeBot('heuristic-v5-balanced-master'),
                  p2: () => makeBot('heuristic-v5-aggro-master') },
});
// → { games, p1Wins, p2Wins, draws, avgTurns, avgSteps,
//     reasons: { glory_zero: N, alt_victory: M },
//     hitLimitCount, elapsedMs }
```

**Ключевое:** `botFactories` — фабрики, не инстансы. Каждая партия создаёт свежих ботов. Это **критично** — боты могут быть stateful, и переиспользование ломает детерминизм.

## 5. Группа 1: Диагностика

Три инструмента для быстрого ответа «что у нас есть».

### 5.1. `list` — что в системе

```bash
pnpm run --filter @aspects/simtools list                # все scope + пресеты + боты
pnpm run --filter @aspects/simtools list main           # детали по scope
pnpm run --filter @aspects/simtools list main strazha   # карты колоды
```

**Что показывает:**
- Все scope с маркером `★` на `main`
- Серии в каждом scope
- Пресеты, доступные в scope (по правилу «все карты внутри серий»)
- Все доступные id ботов

**Когда использовать:** перед любым прогоном — чтобы не передать несуществующий `deckId` или `botName`.

### 5.2. `trace` — пошаговая трассировка

```bash
pnpm run --filter @aspects/simtools trace main strazha divan test-seed-1 heuristic-v5-balanced-master
```

**Что делает:** играет одну партию и выводит **каждую команду** с состоянием до/после. Указывает `✗REJECTED`, если команда отклонена.

**Формат вывода:**
```
── Initial: turn=1 phase=RESTORE active=p1 glory=30/30 inf=0 hand=4 | front p1=[. . . . .] ...
[0] p1: {"type":"ADVANCE_PHASE","playerId":"p1"}
     → turn=1 phase=PLAY active=p1 glory=30/30 inf=1 hand=5 | ...
[1] p1: {"type":"PLAY_CARD","playerId":"p1","cardId":"c3","column":1}
     → turn=1 phase=PLAY active=p1 glory=30/30 inf=0 hand=4 | front p1=[Кукла(0) . . . .] ...
...
── End: winner=p2 reason=glory_zero steps=125
```

**Когда использовать:**
- Найти, на каком шаге бот принял плохое решение
- Понять, почему партия затянулась
- Дебажить конкретный seed

**Совет:** перенаправляй в файл, если партия длинная:
```bash
pnpm run --filter @aspects/simtools trace ... > trace.log
```

### 5.3. `dump-state` — дамп JSON

```bash
pnpm run --filter @aspects/simtools dump-state main strazha divan 50 heuristic-v5-balanced-master state.json
```

**Что делает:** играет N команд и сохраняет `GameState` в JSON.

**Когда использовать:**
- Создать фикстуру для теста
- Сравнить два прогона на бинарном уровне
- Понять «что за состояние на ходу 50»

## 6. Группа 2: Базовые симуляции

### 6.1. `simulate` — серия между двумя колодами

```bash
pnpm run --filter @aspects/simtools simulate main strazha divan 100
```

**Параметры:**
- `<scope>` — имя scope или серии через запятую
- `<p1DeckId>`, `<p2DeckId>` — id пресетов
- `<N>` — партий
- `--mulligan` — включить муллиган

**Что выводит:**
```
──────────────────────────────────────────────
  Scope:     classic, cradle, inner, throne
  P1 deck:   strazha
  P2 deck:   divan
  Games:     100
──────────────────────────────────────────────
  P1 wins:   54 (54.0%)
  P2 wins:   46 (46.0%)
  Draws:     0 (0.0%)
  Avg turns: 28.1
  Avg steps: 137.2
  Reasons:   glory_zero=94 alt_victory=6
  Time:      24000ms
──────────────────────────────────────────────
```

**Когда использовать:** проверить одну конкретную пару, посмотреть базовые метрики.

### 6.2. `matrix` — матрица N×N

```bash
pnpm run --filter @aspects/simtools matrix main 50
pnpm run --filter @aspects/simtools matrix main 50 heuristic-v5-balanced-master strazha,divan
```

**Параметры:**
- `<scope>` — обязателен
- `<N>` — партий на пару (не на весь матрикс!)
- `[botName]` — опционально, default `heuristic-v5-balanced-master`
- `[deck1,deck2,...]` — ограничить набор колод
- `--mulligan`

**Что выводит:** матрицу winrate (P1 perspective). Каждая клетка — `XX% (YYt)`, где `YY` — средняя длина.

```
P1 \ P2       │       strazha          divan      partizany
──────────────┼────────────── ────────────── ──────────────
strazha       │     54% (27t)      60% (28t)      46% (28t)
divan         │     42% (28t)      50% (34t)      40% (31t)
partizany     │     42% (27t)      56% (29t)      48% (27t)
```

**Плюс проверка симметрии:**
```
Симметрия пар (ожидание ≈100%):
  strazha vs divan          102%
  strazha vs partizany       88%  ⚠
  divan vs partizany         96%
```

`88%` означает, что `strazha` выигрывает у `partizany` 46%, а `partizany` у `strazha` 42% — асимметрия. Может быть шум (при N=50 SE≈7%), может быть реальная асимметрия (бот по-разному играет за p1/p2).

**Когда использовать:**
- Оценить баланс пресетов
- Найти доминирующую колоду
- Проверить, что матчапы симметричны (нет side-bias)

### 6.3. `duel` — A/B-тест двух ботов

```bash
pnpm run --filter @aspects/simtools duel main 20 heuristic-v5-balanced-master heuristic-v5-aggro-master strazha,divan
```

**Параметры:**
- `<scope>`, `<N>`, `<botA>`, `<botB>`
- `[deck1,deck2,...]` — ограничить набор колод
- `--mulligan`

**Методология:** для каждой пары колод играются **две зеркальные серии**:
- `X`: `botA@d1` vs `botB@d2`
- `Y`: `botB@d1` vs `botA@d2`

Победы A = `X.p1Wins + Y.p2Wins`. Победы B = `X.p2Wins + Y.p1Wins`.

За счёт смены стороны и сохранения колоды на месте преимущество первого хода и перекос колод **взаимно уничтожаются**. Остаётся чистая разница силы ботов.

**Что выводит:**
```
══════════════════════════════════════════════════
  Duel:    heuristic-v5-balanced-master  vs  heuristic-v5-aggro-master
  Games:   160  (20 per (pair, orientation))
──────────────────────────────────────────────────
  balanced-master wins:  79     (49.38%)
  aggro-master wins:     81     (50.63%)
  Draws:                 0      (0.00%)
──────────────────────────────────────────────────
  Avg turns:  30.1
  Decisive:   160, balanced share: 49.38%, z = -0.16
  → не значимо (p > 0.05)
══════════════════════════════════════════════════
```

**z-статистика** — критична. Если `|z| < 1.96` — разница не значима на уровне p=0.05. То есть 49% vs 51% — это **одно и то же**.

**Когда использовать:**
- Сравнить два профиля ботов
- Проверить, помогает ли новая фича бота (например, новая эвристика)
- Калибровать `mistakeRate` уровней

### 6.4. `first-player` — first-mover advantage

```bash
pnpm run --filter @aspects/simtools first-player main 200
```

**Параметры:**
- `<scope>`, `<N>`
- `[botName]` — default `heuristic-v5-balanced-master`
- `[deck1,deck2,...]`

**Что делает:** для каждой колоды играет `N` mirror-партий (`deck vs deck`), плюс cross-matchups (если несколько колод). Считает **чистое преимущество первого хода**, независимо от того, кто такой «первый».

**Что выводит:**
```
── Mirror: strazha vs strazha ─────────────────
  Games:               200
  P1 went first:       107  (53.5%)
  P2 went first:       93   (46.5%)
  ── Pure first-mover advantage ──
  First player wins:   97   (48.5%)
  Second player wins:  103  (51.5%)
  Advantage:           -1.5 п.п.  (SE ≈ 3.5%, z = -0.42)
```

**Интерпретация:**
- `Advantage ≈ 0` — first-mover отсутствует.
- `Advantage > 3 п.п.` (z > 1.96) — есть реальное преимущество, надо компенсировать второму игроку.
- `Advantage < -3 п.п.` — наоборот, второй игрок сильнее (обычно это баг или особая механика).

**Когда использовать:**
- Раз в итерацию правил — проверить, не появилось ли преимущество.
- После добавления новых механик (например, если `starter` даёт бесплатную карту в руке — это может стать first-mover advantage).

### 6.5. `matchup-heatmap` — визуальная матрица

```bash
pnpm run --filter @aspects/simtools matchup-heatmap main 50
```

**Отличие от `matrix`:** ANSI-цвета.
- 🟢 зелёный — P1 выигрывает >60%
- 🟡 жёлтый — 40-60%
- 🔴 красный — <40%

**Когда использовать:** быстро окинуть взглядом 5×5+ матрицу, найти зоны дисбаланса.

## 7. Группа 3: Анализ карт и колод

### 7.1. `card-stats` — Δ-метрика по картам

```bash
pnpm run --filter @aspects/simtools card-stats main 50
```

**Параметры:** `<scope>`, `<N>`, `[botName]`, `[deck1,deck2,...]`, `--mulligan`.

**Методология.** Для каждой карты считается два числа:
- `wr_play` — winrate партий, где карта **была разыграна**;
- `wr_no_play` — winrate партий, где карта **была в руке, но не разыграна**.

**Δ = wr_play − wr_no_play.**

Это устраняет базовый winrate колоды и отвечает: **«играть карту — лучше, чем не играть?»**

**Что выводит:**

```
─── Топ 15 «ценных» карт (Δ > 0) ──────────────
card                       cost  drawn played  pRate  medT  wr_play  wr_no         Δ
Ростовчанин                   3    566    362  64.0%    18  71.0%  13.2%   +57.8pp
Эксперимент                   1    544    499  91.7%    13  55.3%   2.2%   +53.1pp
...
─── «Мёртвый груз» (playRate < 15%) ───────────
Ворчун                        4    569     75  13.2%  23.5  72.0%  46.0%   +26.0pp
```

**Колонки:**
- `cost` — стоимость карты
- `drawn` — сколько раз карта попадала в руку
- `played` — сколько раз разыграна
- `pRate` — `played / drawn` (доля разыгрывания)
- `medT` — медианный ход розыгрыша
- `wr_play` — winrate когда разыграна
- `wr_no` — winrate когда в руке, но не разыграна
- `Δ` — разница

**Интерпретация Δ:**
- `Δ > +8pp` — сильный сигнал «карта ценна».
- `Δ +3..+8pp` — умеренный.
- `Δ −3..+3pp` — в пределах шума (или карта ситуативная).
- `Δ −8..−3pp` — чаще играется в проигранных партиях.
- `Δ < −8pp` — устойчивая корреляция с поражениями.

**Интерпретация playRate:**
- `< 15%` — «мёртвый груз»: в руке есть, но бот почти не играет.
- `15-50%` — ситуативная.
- `> 50%` — «must-play».

**Крайне важно:**

Δ — это **корреляция, не причинность**. Win-more карты имеют высокий Δ автоматически (играются только в победных партиях). Comeback-карты — низкий. **Всегда смотри на cost и контекст.**

**Что реально показали текущие данные (900 партий):**
- `Ростовчанин` (cost 3): Δ +57.8pp, playRate 64%. **Значит:** играет на ходу 18 в среднем — только когда партия затянулась. Не карта «хорошая», а карта «играется только в победных партиях».
- `Ворчун` (cost 4): Δ +26pp, playRate 13% — единственная мёртвая. Играется на ходу 23.5, но когда играется — 72% winrate. **Значит:** карта сильная, но cost 4 не окупается — не попадает в игру.
- **0 карт с cost 5+ в пуле.**

**Параметры:** `<scope>`, `<N>`, `[botName]`, `--mulligan`.

**Что делает.** Для каждой пары пресетов `(A, B)` играет `N` партий. Собирает winrate каждой колоды **в среднем по всем матчапам**.

### 8.2. `turn-outcome` — winrate по длине партии

```bash
pnpm run --filter @aspects/simtools turn-outcome main 50
```

**Что делает.** Играет партии, разбивает их по бакетам длины (`10-14`, `15-19`, ..., `45-60`). Для каждого бакета считает:
- Сколько партий
- Winrate P1
- Средний glory победителя
- Средний glory проигравшего
- Распределение причин победы

**Что выводит:**
```
turns     games   p1_wr   avg_winner_glory  avg_loser_glory   reasons
15–19     42      69.0%   27.6              0.5               glory_zero:40 alt_victory:2
20–24     103     54.4%   27.9              0.7               glory_zero:94 alt_victory:9
25–29     107     43.0%   25.6              0.1               glory_zero:103 alt_victory:4
...
45–60     15      53.3%   9.9               0.0               glory_zero:15
```

**Ключевые сигналы:**
- `avg_loser_glory` везде ~0 → партии заканчиваются **только полным уничтожением**. Нет «почти умер» — есть «умер».
- `avg_winner_glory` падает с 27.6 (короткие) до 9.9 (долгие) → **долгие партии — это взаимное истощение**.

**Когда использовать:**
- Диагностика pace — есть ли «застревающие» бакеты.
- Проверка гипотезы «P1 имеет преимущество в определённом диапазоне».
- Понять **как** заканчиваются партии.

## 9. Группа 5: Pace и боевая эффективность

### 9.1. `pace-report` — pace-анализ партии

```bash
pnpm run --filter @aspects/simtools pace-report main 100
```

**Что делает.** Играет `N` партий на пару, собирает через `onAfterCommand` метрики по ходу партии.

**Что выводит 5 блоков:**

**1. Длина партии:**
```
Mean: 29.1 ходов, Median: 28
Гистограмма по бакетам (bucket = 5): 0-4, 5-9, ..., 60-64
```

**2. Стоимость разыгранных карт:**
- Распределение cost (0..10)
- Avg cost, median
- Доли: дешёвых (0-2), средних (3-4), дорогих (5+)

**3. Средний cost по ходам:**
```
Ходы 1-5:  avg=1.40
Ходы 6-10: avg=1.88
Ходы 11-15: avg=2.10
...
Ходы 26-30: avg=2.31
```

Если растёт медленно — экономика не даёт играть дорого. Если плавно до 4-5 — работает.

**4. Средний размер руки:**
```
Ходы 1-5:  avg=5.31
Ходы 6-10: avg=6.33
...
Ходы 26-30: avg=9.84
```

Если рука растёт к 9-10 — бот не может «сбросить» накопленное. Если стабильно 3-4 — всё ок.

**5. Неистраченное влияние:**
```
Среднее: 0.24 / 10
Медиана: 0
```

Если 0-1 — влияние тратится полностью. Если 4-6 — бот не может потратить, что копит. Если >7 — экономика переполнена.

**6. Idle-ходы:** сколько ходов без `PLAY_CARD`/`ATTACK`/`USE_ABILITY`.

**7. Карты, умершие в течение 1 хода:** процент.

**8. Вехи партии:** на каком ходу первый розыгрыш, первая смерть, первый захват нейтрала, первое падение glory <20, <10.

**9. Причины завершения.**

**10. Нейтралы к концу:** сколько под P1 / под P2 / ничейных.

**Что реально показали текущие данные:**

- **Рука растёт линейно до 9.8.** Главная причина 28+ ходов. Бот берёт 1 карту/ход, играет 0.85. Накопление.
- **Неистраченное влияние 0-1 в 96.3% случаев.** Влияние не bottleneck.
- **Cost по ходам медленно растёт: 1.4 → 2.31.** Дороже 3+ почти не играется.
- **Первая смерть на ходу 5.4, glory <20 на ходу 17.8.** Первые 17 ходов — «нулевые», никто не продавливает.

### 9.2. `combat-efficiency` — эффективность боя

```bash
pnpm run --filter @aspects/simtools combat-efficiency main 100
```

**Что делает.** Играет `N` партий, для каждой сыгранной карты отслеживает:
- Когда разыграна (turn)
- Когда умерла (turn)
- Сколько атак сделала
- По кому атаковала (guild / card / neutral)

**Что выводит:**

**Судьба карт:**
- Умерли без единой атаки (%)
- Атак на карту в среднем
- Медианная / средняя жизнь (в ходах)

**Куда бьют:**
- Атак по картам (%)
- Атак по гильдии (%)
- Атак по нейтралам (%)

**Атаки по фазам COMBAT:**
- Всего фаз у P1 / P2
- Фаз без атак (%)
- Атак за партию
- Первая атака (средний turn)

**Интерпретация (автоматическая):**
- `died_without_attack > 40%` — attrition-паты. Карты не окупаются. Нужно живучее или дешевле.
- `died_without_attack > 25%` — на грани.
- `attacks_per_life < 1` — карта не окупает розыгрыш.
- `median_lifespan < 2` — карты почти не живут.
- `face_share > 60%` — боты игнорируют обмен, rushят.
- `face_share < 30%` — боты не понимают, когда закрывать.
- `phase_with_attack < 50%` — половина COMBAT-фаз «пустые».

**Что ожидаем увидеть** (по остальным данным):
- first_attack ~5
- died_without_attack 20-40%
- attacks_per_life 1.5-2

Если `died_without_attack > 40%` — подтверждается гипотеза «pace застревает на attrition».

### 9.3. `missed-lethal` — детектор упущенных леталов

```bash
pnpm run --filter @aspects/simtools missed-lethal main 100
```

**Методология.** На **начало каждой COMBAT-фазы** проверяем:
- Фронт оппонента пуст
- Суммарная сила неистощённых юнитов активного игрока ≥ glory оппонента
- Glory оппонента > 0

Если все три — это **летальный ход**. Если фаза закончилась, а glory оппонента всё ещё > 0 — это **missed lethal** (AI-баг или чрезмерная осторожность).

**Что выводит:**
- Всего lethal turns (было доступно)
- Missed lethal (не убил)
- Miss rate (%)
- Первые 20 упущенных ситуаций с деталями: game, turn, player, available_power, opp_glory

**Интерпретация:**
- `Lethal turns = 0` — **игра не доходит до состояния добивания**. Это подтверждает, что pace-проблема в структуре игры (фронт постоянно занят), а не в AI.
- `Miss rate = 0%` — бот идеален, когда летал есть.
- `Miss rate > 5%` — AI-баг. Смотрим детали: если power >> glory (наприм. 20 vs 5), бот «тупит сильно». Если power ≈ glory (10 vs 10), ошибка на грани.

## 10. Группа 6: Поиск колод

### 10.1. `deck-optimizer` — генетический поиск

```bash
pnpm run --filter @aspects/simtools deck-optimizer main --out best-decks.json
```

**Параметры:**
- `<scope>` — обязателен
- `--pop N` — размер популяции (default 12)
- `--gen N` — число поколений (default 12)
- `--eval N` — партий на оценку особи (default 30)
- `--elite N` — размер элиты (default 2)
- `--bot NAME` — бот (default `heuristic-v5-balanced-master`)
- `--seed STR` — seed для воспроизводимости
- `--out FILE` — сохранить топ-колоды в JSON

**Методология.**

1. **Инициализация.** Генерируются `pop` случайных колод с дедупликацией. Каждая валидируется:
   - ровно 30 карт
   - ≤4 серий
   - ≤5 копий одной Личности
   - ≤2 копий одного Аспекта
   - ≤1 легендарки одного id

2. **Оценка.** Для каждой особи считается fitness = winrate против **смеси**:
   - всех базовых пресетов scope'а
   - top-5 особей прошлой генерации (co-evolution)

   `gamesPerEval` партий на особь, стороны чередуются (P1 / P2).

3. **Селекция.** Топ-`elite` сохраняются. Плюс 2 случайных из середины (разнообразие).

4. **Репродукция.**
   - Crossover: смешать карты двух родителей, очистить.
   - Mutation: заменить 15% карт на случайные.

5. **Финальная проверка.** Топ-5 переоцениваются на **100 партиях** против **всех** базовых пресетов (без co-evolution, чтобы избежать overfitting).

**Что выводит:**
```
Gen  1/12: best=70.0% avg=36.7% worst=20.0% (27s)
Gen  2/12: best=60.0% avg=26.7% worst=10.0% (59s)
...
Gen 12/12: best=72.0% avg=48.2% worst=30.0% (800s)

─── Топ-5 колод (финальная оценка) ────────────
#1  winrate=62.3%  series=[classic, cradle, inner, throne]
   cost: 1💰×4 2💰×5 3💰×13 4💰×6 5💰×1 6💰×1
   1× Бюрократ (3💰)
   ...
```

**Что важно:**

- **`best` может скакать.** При `gamesPerEval=30` SE ≈ 9pp. Разница 60↔70 — статистически не значима. Смотри на `avg`, а не на `best`.
- **Финальная оценка важнее промежуточной.** Если промежуточный `best` был 70%, а финальный 62% — значит co-evolution дала overfit, колода натренировалась на топ-5, но слабее против базовых.
- **Cost curve топа** — ответ на «можно ли играть дорогие карты». Если в топе cost 5-6 — да, окупаются.
- **Дедупликация через signature.** Если генерация не может набрать `pop` уникальных — уменьши `--pop` или упрости `randomDeck`.

**Производительность:**

Дефолты: 12×12×30 + 10×100 = 4320 + 1000 = **5320 партий**. При 240мс/партия ≈ **21 минута**.

Быстрая версия: `--pop 8 --gen 6 --eval 20` ≈ **~2 минуты**.

**Когда использовать:**
- Найти колоду, которая бьёт базовые пресеты.
- Понять, какие карты вообще работают (что optimizer выбирает).
- Проверить, окупаются ли карты 5+.

**Ограничение:** оптимизатор ищет «колоду против бота-мастера», не «колоду против живого игрока». Результаты — **сигнал**, а не «оптимальная колода».

## 11. Методология и интерпретация

### 11.1. Детерминизм

Движок детерминирован: `createGame(seed)` + команды → `GameState`. Значит:
- Одинаковый `seed` → одинаковая партия (при одинаковых ботах).
- **Разные seeds в серии** — обязательны для статистики. `runSeries` генерирует seeds `${series.join('+')}-${p1}-${p2}-${i}`, что обеспечивает уникальность.

### 11.2. Детерминизм ботов

Боты **stateful**, но детерминированные. Внутри `HeuristicBot` — seeded RNG, никаких `Math.random()`.

**Важно:** создавай **новых ботов** на каждую партию. `botFactories` в `runSeries` — именно для этого. Переиспользование одного инстанса ломает детерминизм.

### 11.3. Статистическая значимость

Ключевые правила:
- `N < 30` — не значимо, только для smoke-test.
- `N = 50` — грубая картина, SE winrate ≈ 7pp.
- `N = 100` — норм, SE ≈ 5pp.
- `N = 200` — хорошо, SE ≈ 3.5pp.
- `N = 500` — уверенно, SE ≈ 2pp.

**z-статистика** — всегда смотри. `|z| < 1.96` = p > 0.05 = **не значимо**.

Для разницы между двумя вариантами:
```
z = (p1 - p2) / sqrt(p1*(1-p1)/n1 + p2*(1-p2)/n2)
```

### 11.4. Корреляция vs причинность

`card-stats`, `keyword-stats`, `deck-optimizer` — **корреляционные**. Они показывают: «карта X часто в победных партиях», не «карта X **делает** победу».

- Win-more карты (играются только в выигранных) — высокий Δ.
- Comeback-карты (играются только в проигранных) — низкий Δ.
- Сильные карты, которые не влезают в колоду (cost 5+) — низкий playRate, средний Δ.

### 11.5. Что важно смотреть в первую очередь

**Для баланса карт:**
1. `card-stats` — Δ и playRate.
2. `deck-diff` — сравнить с существующим.

**Для pace:**
1. `pace-report` — длина, cost, рука, влияние.
2. `combat-efficiency` — attrition vs tempo.
3. `missed-lethal` — есть ли AI-баги.

**Для меты:**
1. `meta-report` — общая картина.
2. `matrix` / `matchup-heatmap` — матчапы.
3. `turn-outcome` — как заканчиваются.

**Для AI:**
1. `duel` — сравнить ботов.
2. `missed-lethal` — есть ли баги.
3. `first-player` — нет ли системного bias.

## 12. Типичные сценарии

### 12.1. «Я добавил 5 новых карт. Как проверить?»

1. `pnpm --filter @aspects/cards build` — пересобрать cards.
2. `pnpm --filter @aspects/cards validate` — проверить, что данные корректны.
3. `pnpm run --filter @aspects/simtools list main <deck>` — убедиться, что новые карты попали в пресет.
4. `pnpm run --filter @aspects/simtools deck-diff main <old> <new>` — сравнить cost-кривые.
5. `pnpm run --filter @aspects/simtools card-stats main 100` — есть ли у новых карт playRate > 15%.
6. `pnpm run --filter @aspects/simtools meta-report main 100` — общий winrate пресетов не сломался.

### 12.2. «Хочу понять, почему игра затянута»

1. `pace-report main 100` — есть ли сигналы (рука растёт, cost медленно, влияние не тратится).
2. `combat-efficiency main 100` — attrition? face share?
3. `missed-lethal main 100` — есть ли missed lethal.
4. `turn-outcome main 100` — как распределена длина.
5. Прочитать интерпретации, найти главную.

### 12.3. «Хочу сравнить двух ботов»

1. `duel main 50 <botA> <botB>` — z-статистика.
2. Если z значим — бот A сильнее.
3. Если не значим — увеличь N.

### 12.4. «Хочу найти новую колоду»

1. `deck-optimizer main --pop 12 --gen 10 --eval 30`.
2. Смотрим топ-5: cost-curve, карты.
3. Проверяем финальный winrate — если < 55%, оптимизатор ничего не нашёл (все колоды примерно равны).
4. Если > 65% — потенциальная доминирующая колода, добавить в пул или nerf.

### 12.5. «Нужно проверить, что first-player не сломан»

1. `first-player main 200` после каждой итерации правил.
2. Если `Advantage > 3 pp` — сломали, надо компенсацию.

### 12.6. «Бот упал на каком-то seed — что делать?»

1. `trace main <deck1> <deck2> <seed> <botName> > trace.log`
2. Смотрим в конце — `no command (bot returned null)` или `✗REJECTED`.
3. Если rejected — баг в боте (невалидная команда).
4. Если null — баг в логике (bot не нашёл команду).

## 13. Troubleshooting

### 13.1. `Unknown deck`

**Проблема:** `deckId` не найден в scope.

**Решение:**
- `pnpm run --filter @aspects/simtools list <scope>` — список валидных deckId.
- Проверь, что пресет использует только карты серий из scope.

### 13.2. `Unknown bot`

**Проблема:** `botName` не в списке.

**Решение:**
- `pnpm run --filter @aspects/simtools list` — все 36 ботов.
- Формат: `heuristic-v5-<profile>-<level>`.

### 13.3. `Empty scope`

**Проблема:** `resolveScope(<arg>)` вернул пустой массив.

**Решение:**
- Проверь имя: `main`, `azeroth`, `svo`.
- Для явного списка — через запятую без пробелов: `classic,throne`.

### 13.4. `Each deck must have exactly 30 cards`

**Проблема:** в `runOneGameRaw` передали `string` вместо `string[]`.

**Решение:**
- Для `deck-optimizer`, `keyword-stats`, `combat-efficiency` — передавай `deck.cards` (массив card ids), не `deck.id`.

### 13.5. `hitLimitCount > 0`

**Проблема:** партия прервана по `maxSteps` или по rejected-команде.

**Решение:**
- Trace проблемного seed: `trace ... <seed> <bot>`.
- Если rejected — баг бота.
- Если timeout — партия не сходится, возможно, новый баг движка.

### 13.6. `hit step limit: N > 0` в pace-report

**Проблема:** некоторые партии не завершились за `maxSteps = 20000`.

**Решение:**
- Обычно это редко (1-2%). Если много — trace.
- Проверь `winner_reason` в выводе.

### 13.7. `Could not generate N valid decks`

**Проблема:** `deck-optimizer` не смог набрать популяцию (все колоды дубликаты или невалидные).

**Решение:**
- Уменьши `--pop`.
- Проверь, что в scope достаточно карт (нужно >30 уникальных).

### 13.8. `pnpm --filter X list` — работает не так

**Проблема:** встроенный `list` перехватывает команду.

**Решение:** всегда `pnpm run --filter X <script>` (с `run`).

### 13.9. `Cannot find module @aspects/simtools`

**Проблема:** пакет не собран или не установлен.

**Решение:**
```bash
pnpm install
pnpm --filter @aspects/simtools build
```

### 13.10. Боты играют по-разному на одинаковом seed

**Проблема:** бот stateful, используется один инстанс.

**Решение:** всегда `botFactories: { p1: () => makeBot(name), p2: () => makeBot(name) }` — свежие боты на партию.

## Финальные заметки

### Что учесть при добавлении нового инструмента

1. **Импорты.** Из `@aspects/engine`, `@aspects/cards`, `@aspects/bot` — напрямую. Из `simtools` — только `runner` и `types`.
2. **Не дёргай `createGame` напрямую.** Используй `runOneGame` / `runOneGameRaw` / `runSeries`. Это даёт детерминизм и `onAfterCommand`.
3. **CLI.** Первый аргумент — scope. Далее — параметры. Валидация `deckId`/`botName` — обязательно.
4. **Вывод.** Числовые таблицы — с `pad()`. Агрегаты — с интерпретацией (что означает число).
5. **Производительность.** 240мс на партию × N. Для инструмента на 500 партий — 2 минуты. Если больше — уменьшай N или добавляй checkpoint.

### Что учесть при интерпретации

1. **Корреляция ≠ причинность.** Особенно в `card-stats` и `keyword-stats`.
2. **Всегда смотри `n`.** Δ +50pp на `n=20` — шум.
3. **Сравнивай с базовыми метриками.** Winrate 60% — хорошо или плохо? Зависит от среднего (обычно 50% в mirror).
4. **Помни про ограничения.** Все инструменты — про **текущий** бот. Если поменяется `HeuristicBot`, сдвинутся все метрики.

### Где обновлять этот документ

При добавлении нового скрипта:
1. Добавь раздел в соответствующую группу.
2. Обнови оглавление.
3. Если меняется `runner` API — обнови раздел 4.
